# Законченная механика вызовов (root → субагенты)

## 1. Инвентарь агентов

| Агент | Статус | Роль | Вход | Выход |
|---|---|---|---|---|
| `audit-factcheck` | есть | актуальность/фидельность | бриф | SGR (audit-factcheck/v1) + блок «ФАКТ-ЧЕК» (≤15 строк) |
| `audit-empiric` | есть | реальные прогоны, замеры, дифференциалы | бриф + факт-чек | SGR (audit-empiric/v1) |
| `audit-invariant` | есть | инварианты/контракты/жизненный цикл | бриф + факт-чек | SGR (audit-invariant/v1) |
| `audit-arbiter` | есть | разбор спорных пунктов | только противоречия + evidence | SGR (audit-arbiter/v1): подтверждён/опровергнут/недоказуем + призма (prism) |
| `audit-meta` | есть | аудит отчётов | отчёты пары + отчёт ред-тима (на воротах) + свод `summary-<id>.md` | SGR (audit-meta/v1): gate / closing_list / coverage_gaps |
| `audit-redteam` | есть | приёмочный прогон (ворота) | бриф + заявка + свод | SGR (audit-redteam/v1) |
| `fix-runner` | есть | правки по списку «к закрытию» (единственный пишущий субагент) | список находок + критерии | SGR (fix-runner/v1) |
| `orchestrator` | есть | универсальный root-оркестратор (`mode: primary`) | цель/задача | готовый результат (аудит — встроенный режим) |

Все, кроме `orchestrator`: `mode: subagent`, `shell` разрешён (правило `shell allow` в `permissions`), универсальные (без проектной конкретики). Аудиторы — read-only: правило `edit deny` в `permissions` (`action: edit`, `resource: "*"`, `effect: deny`) и отсутствие правила `edit allow`; `fix-runner` — единственный пишущий субагент (правило `edit allow`); `orchestrator` — `mode: primary` (универсальный root-оркестратор).

Примечание (K6). Рекомендуется второй вендор для `audit-arbiter` / `audit-redteam` (и/или для второго голоса аудиторской пары из другого вендора): гетерогенность панели повышает recall (см. `research/ready-agent-kits-vs-ours-2026-10.md`). До выбора модели — по умолчанию deepseek. Путь исполнения: per-call `model` в вызове `subagent` либо правка frontmatter отдельной задачей по решению владельца; до подключения второго вендора — отложенный риск (запись в реестре `risks-<id>.md`).

## 2. Формы вызовов

`subagent({agent, prompt, background?, sessionID?, model?})`

- **foreground** — короткие зависимые шаги (факт-чек, арбитр, мета).
- **background** — долгие (пара, ред-тим); два вызова в одном блоке = параллельный запуск.
- **sessionID** — только для resume (re-audit и верификация — продолжение той же сессии роли); вызов без сохранённого sessionID = дефект шага (новая сессия вместо продолжения).
- **model** — только по решению владельца (per-call смена вендора; см. примечание K6 в §1): гетерогенность панели — осознанный выбор, не дефолт.

## 3. Фазы

Нумерация: «Фаза N» — фазы этого документа (`call-mechanics.md`); «[N]» — шаги цикла из `process-ready-loop.md`. Ссылки между документами указывают пространство имён явно.

### Фаза 0. Подготовка (root, вызовов нет)
Создаёт состояние X0 (слепая песочница для первичного аудита; с дельтой — для повторного), пишет `case-<id>.md`, заводит `risks-<id>.md`.

Шаблон брифа:
```
# Аудит <id>: <название>
Состояние: <путь, коммит/диапазон; база сравнения>
Контекст: <цель изменения, что заявлено автором>
Материалы: <дифф/пути; чего НЕТ: напр., git-история недоступна>
Доступные данные и бюджет: <корпуса/справки/стенды (пути); разрешена ли сборка
  (изолированный target во временном каталоге); лимит времени; что запрещено>
Ограничения: read-only; эксперименты во временном каталоге; не публиковать
Контракт отчёта: SGR (резюме + ```json по схеме роли)
```

### Фаза 1. Факт-чек (1 foreground-вызов)
```
subagent({
  agent: "audit-factcheck",
  prompt: "Прочитай бриф <case>. Сверь тезисы и премисы с живой реальностью
   (git, upstream issues/PR, текущий код): что устарело, что уже сделано,
   какие обещания/доки разошлись. Верни SGR + блок «ФАКТ-ЧЕК» (≤15 строк)
   для передачи аудиторам."
})
```
Решение root: «устарело/уже сделано» → **СТОП**, пересмотр задачи. Иначе — извлечь блок.

### Фаза 2. Пара (2 background-вызова в одном блоке)
```
subagent({agent:"audit-empiric",  background:true,
  prompt:"Бриф <case>. ФАКТ-ЧЕК:\n<блок>. Выполни по своей роли; верни SGR."})
subagent({agent:"audit-invariant", background:true, prompt:"… то же …"})
```
root сохраняет оба sessionID из ответов и **ждёт уведомлений** (не поллит).

### Фаза 3. Свод (root, вызовов нет)
- Парсит JSON-блоки: вердикты, открытые MAJOR, полнота self_check/lines.
- Конфликт = противоречие по одному месту/классу либо несовпадение вердиктов по пункту.
- Невалидный отчёт: пустой/битый/неразбираемый отчёт или вердикт вне enum → дефект шага: resume той же сессии с требованием перевыпустить SGR; повторный сбой → эскалация владельцу.
- Порождает **свод-артефакт** `reports/summary-<id>.md` (определение — §4): по каждой MAJOR — `{id, verifier_role, verdict, evidence}`; явный refuted-список; принятые риски; ревизия состояния.
- Ветвление: оба ready и MAJOR=0 → релизные ворота: **Фаза 8 (ред-тим) → Фаза 6 (мета)**; коммит/PR — Фаза 7; иначе → Фаза 3.5 (верификация MAJOR) → Фазы 4/5.

### Фаза 3.5. Верификация MAJOR-находок (перекрёстная)
Каждая MAJOR-находка проходит независимую проверку **сессией противоположной роли** (родственным аудитором, не автором находки) — resume его сессии:
```
subagent({agent:"audit-<sibling>", sessionID:<сессия>,
  prompt:"Находка <id> контрагента: <текст>. Evidence автора: <команда→вывод>.
   Ревизия состояния: <хэш каталога/коммит>. Подтверди или опровергни своим
   воспроизведением; дефолт — не подтверждена. Верни: verdict + evidence."})
```
Схема ответа верификатора (обязательна):
```
{"id": "<id находки>", "verifier_role": "<роль верификатора>",
 "verdict": "confirmed|refuted|partial|unavailable", "evidence": "<команда → сырой результат>"}
```
Правила:
- `verifier_role` ≠ роль автора находки — верифицирует не тот, кто нашёл.
- `partial` и `unavailable` трактуются как **«не подтверждена»** — в правки находка не идёт.
- Сбой/таймаут верификатора → «не подтверждена» (`unavailable`) + запись в шум аудита (см. §5).
- Fail-closed: без явного подтверждения своим воспроизведением находка считается **не подтверждённой**. При споре — Фаза 4 (арбитр). Опровергнутые (`refuted`) собираются в список refuted свода и переходят в шум аудита.
- Ревизия состояния фиксируется вместе с вердиктом: верификация действительна только для той ревизии, на которой сделана (см. §7).
- Статусы верификации (`verifier_role` + `verdict` + evidence) дописываются в свод `reports/summary-<id>.md`.
- Взаимное воспроизведение: если MAJOR-находка независимо воспроизведена обеими ролями в их собственных прогонах (свои команды, одна ревизия состояния) — это засчитывается как перекрёстная верификация; отдельный прогон верификатора не требуется, в свод пишутся обе стороны (`verifier_role` каждой роли + evidence).

### Фаза 4. Арбитр (условный; только при конфликтах)
```
subagent({
  agent: "audit-arbiter",
  prompt: "Спорные пункты:
   1) <пункт> — evidence A: <команда→вывод>; evidence B: <команда→вывод>.
   По каждому: подтверждён/опровергнут/недоказуем + способ проверки +
   призма (reproducibility|contract|falsification|not_applicable;
   при нескольких — массив призм). Ничего кроме этого не проверяй."
})
```
Итог: confirmed → правка; refuted → снять + запись в шум аудита; undecidable → решение владельца: root оформляет вопрос, фиксирует риск (`risks-<id>.md`) и эскалирует.

### Фаза 5. Правки и повтор
- Правки начинаются только после фиксации вердикта свода (и верификации/арбитража). До вердикта — не править.
- Правки по порогу: микроправки (1–3 строки, тексты/доки) — root сам; средние/крупные (мультифайл, логика, тесты) — субагент `fix-runner`; спорное до делегирования решает root (после арбитра).
- Вызов фиксера:
```
subagent({agent:"fix-runner", prompt:"К закрытию:\n1) <id | локация | механизм |
 класс/область (пути + правило поиска однотипных мест) | repro-до |
 критерий-после | severity>\nГраницы: <пути/ветка>; бюджет/лимит: <время, число
 правок>; коммит: <да/нет, сообщение fix-<round>>. Верни fix-runner/v1."})
```
- Root проверяет дельту (`git show --stat` + ключевой прогон) до re-audit и обновляет реестр.
- Стенд раунда (если в комплекте поставляется проверочный стенд — инструменты `tools/kit-verify` (верификатор) и `tools/kit-sync` (синк копий + снимок) каталога комплекта; в раундах по другим проектам — только если стенд явно включён в границы вызова): baseline → правки → синк копий и повторный прогон стенда; дельта baseline→after прикладывается к отчёту (поле `stand`).
- **re-audit = resume тех же сессий**:
```
subagent({agent:"audit-empiric", sessionID:<emp>, background:true,
  prompt:"Правки: <диапазон/коммиты + фактический список изменённых файлов>; закрыто: <…>. Проверь закрытие своих
   находок и отсутствие регрессий на новом состоянии; верни обновлённый SGR."})
subagent({agent:"audit-invariant", sessionID:<inv>, background:true, prompt:"… то же …"})
```
- → фаза 3. С 3-го круга нерешённые пункты — арбитр поштучно; повторяющиеся ложные — закрыть как шум.

### Фаза 6. Мета-аудит (обязателен на релизных воротах = публикация релиза/тега)
```
subagent({
  agent: "audit-meta",
  prompt: "Отчёты: <пути>; свод: <путь к summary-<id>.md>. Проверь статусы
   верификации MAJOR в своде (verdict + verifier_role); evidence у каждой
   находки; полнота
   линий/пунктов; нет ли «зелёные тесты = проверено». Верни pass/fail
   по каждому отчёту и список несоответствий."
})
```
`audit-meta` → fail: ship запрещён; адресный список несоответствий → правки/пересборка отчётов → повторная мета; повторный fail → эскалация владельцу. Вердикт меты несёт единственный блокирующий агрегат `gate` (pass|fail; `verdict` — синоним `gate`); дополнительно `closing_list` (id находок ред-тима, обязательных к закрытию) и `coverage_gaps` — что не удалось проверить. `gate`=pass требует «`closing_list` пуст/закрыт»; принятие `coverage_gaps` — только владельцем, с записью в `risks-<id>.md`.

### Фаза 7. Лёгкий выход (коммит/PR)
Условие: все роли ready, MAJOR=0, риски приняты, **правок после вердикта нет** (иначе — повторный прогон или явное понижение вердикта, см. §7). В PR — строка «audit loop: N кругов; вердикты ready; принятые риски: …».

### Фаза 8. Ворота (релиз)
- Заморозить кандидат Xn.
```
subagent({agent:"audit-redteam", background:true,
  prompt:"Бриф <case>. Заявка автора: <…>. Свод прошлых кругов: <…>.
   Мандат фальсификации: воспроизведи каждое заявление своими инструментами;
   доступные данные: <корпуса/стенды>; генерируй крафтовые входы. Верни SGR."})
```
- not_ready → повтор Фаз 3.5–5 (верификация MAJOR + правки, resume ред-тима); затем — Фаза 6 (`audit-meta`, см. выше; без дублирования правил). Вердикт ворот несёт `closing_list` (id находок, обязательных к закрытию для pass) и `coverage_gaps` (что не удалось проверить/атаковать).
- MAJOR-находки ред-тима проходят такую же верификацию (Фаза 3.5): верификатор — сессия противоположной роли по указанию root; спор → арбитр (Фаза 4).
- **Ship-условие (единое для всех документов):** SHIP ⟺ `meta.gate`=pass ∧ `closing_list` пуст/закрыт ∧ `coverage_gaps` приняты владельцем (запись в `risks-<id>.md`); иначе ship запрещён.

## 4. Передача данных

| Откуда → Куда | Что | Формат |
|---|---|---|
| root → всем | бриф `case-<id>.md` (один на всех) | файл |
| factcheck → пара | «ФАКТ-ЧЕК» ≤15 строк | блок в промпте |
| пара → root | полные SGR-отчёты | JSON-блоки |
| root → арбитр | только спорные пункты + evidence обеих сторон | список |
| root → верификатор | находка MAJOR (id, текст, evidence автора, ревизия состояния) | текст |
| root → fix-runner | список «к закрытию» (id, локация, класс/область, repro-до, критерий-после, severity) + границы/бюджет | текст |
| root → re-audit | дельта правок + фактический список изменённых файлов + список закрытого | текст |
| root → redteam | заявка + свод всех кругов | текст |
| redteam → root | SGR | JSON |
| root → meta | отчёты (пути) + свод `reports/summary-<id>.md` | файл |
| meta → root | SGR (audit-meta/v1) | JSON |

### Свод-артефакт `summary-<id>.md` (в `reports/`)

Материализованная сводка круга — вход Фазы 6 (`audit-meta`) и опора привязки вердикта к состоянию. Состав:
- по каждой MAJOR — `{id, verifier_role, verdict, evidence}`;
- refuted-список — явным разделом, даже если пуст (`verifications: —`);
- принятые риски (id/суть + ссылка на `risks-<id>.md`);
- ревизия состояния (хэш каталога/коммит), на которой зафиксированы вердикты и верификация.

Пишут: Фаза 3 — создаёт/обновляет; Фаза 3.5 — дописывает статусы верификации; Фаза 5 — закрытое/принятое; ревизия состояния — при каждой фиксации вердикта.

Сохранение (все документы кита): SGR-отчёты всех ролей, включая **SGR-отчёты `fix-runner`**, и свод `summary-<id>.md` сохранять в `reports/` (рядом с `case-<id>.md` и `risks-<id>.md`); отчёты — машиночитаемый вход следующих фаз (мета, верификатор), а не только текст в чате.

### Инструменты `audit_*` (если зарегистрированы плагином)

- ревизия состояния → `audit_snapshot` (aggregate = хэш каталога): фиксируется вместе с вердиктом и верификацией;
- отчёт роли → `audit_validate_report` (путь или текст): `valid=false` → дефект шага, resume той же сессии с требованием перевыпустить SGR; не пропускать `warnings`;
- sessionID ролей, их модель и стоимость → `audit_sessions`;
- инструменты недоступны — работаем вручную, как прежде.

## 5. Отказы и восстановление

- Субагент упал/прерван → resume с «продолжи с места остановки, не переделывай»; при `Agent not found` — проверить файлы агентов. Источники не смешивать: определения агентов — каталог комплекта (`agents/`), копии — глобальный каталог агентов вашего харнесса (путь зависит от ОС) и проектный каталог агентов харнесса; снимок/восстановление конфигурации — `tools/config-guard` (хранитель конфигурации комплекта, если поставляется), не агенты.
- Модель/провайдер недоступны → подождать/сменить модель по решению владельца, сессии сохранить.
- Ограниченная среда (Code Mode: действия только через `execute`+каталог, `subagent` недоступен) → аудиторский цикл не запускается; итог — «готово; штатный аудит отложен» с ревизией и планом прогона (§8).
- `audit-arbiter` недоступен или бюджет исчерпан → root разбирает спорный пункт поштучно по фактам/цитатам и фиксирует как риск и эскалирует владельцу.
- Верификатор MAJOR (Фаза 3.5) сбойнул или не уложился в таймаут → находка считается **не подтверждённой** (`unavailable`), в правки не идёт, факт фиксируется в шуме аудита.
- Рестарт сервера посреди прогона → resume по sessionID.
- Никакого поллинга: уведомления приходят автоматически.

| Шаг | Время |
|---|---|
| факт-чек | 1–2 мин |
| пара (параллельно) | 5–10 мин каждый |
| арбитр | 1–3 мин на пункт |
| верификация MAJOR (Фаза 3.5) | 1–3 мин на находку |
| мета (Фаза 6) | 1–3 мин на отчёт |
| fix-runner (Фаза 5) | по бюджету вызова (число правок / время) |
| круг цикла (свод+правки+повтор) | 10–20 мин |
| ред-тим (ворота, Фаза 8) | часы |

## 7. Инварианты процесса

- root не аудирует и не подменяет вердикты; писатель в каждый момент один: root (микроправки) или `fix-runner` (средние/крупные).
- Аудиторы read-only; проектная конкретика — только в брифе.
- Правки начинаются только после фиксации вердикта свода (и верификации MAJOR/арбитража). До вердикта — не править.
- MAJOR-находки входят в правки только после независимой верификации (Фаза 3.5); дефолт верификатора — «не подтверждена» (fail-closed).
- Спорное — `audit-arbiter`; недоказуемое → решение владельца: root оформляет вопрос, фиксирует риск и эскалирует; повторяющееся ложное — шум и закрытие.
- Вердикт и верификация фиксируются вместе с ревизией состояния (хэш каталога/коммит); любая правка после фиксации вердикта → повторный прогон (re-audit) либо явное понижение вердикта.
- «Ready» = все находки закрыты или явно приняты; цикл живёт до полного ready.

## 8. Ограниченные среды (Code Mode)

Среда сессии может смениться в ходе работы: прямые инструменты заменяются вызовом через `execute`+каталог, инструмент `subagent` пропадает — аудиторский цикл в такой сессии невозможен.

- Преflight: перед аудиторской фазой проверь наличие `subagent`; нет — цикл не запускай.
- Статус итога: «готово; штатный аудит отложен». В итог: ревизия состояния (коммит/хэш каталога), компенсирующие проверки списком (явно как проверки), план прогона в обычной сессии.
- Запрещено: выдавать самопроверку/`ai`-ревью за независимый аудит; помечать задачу прошедшей аудит; писать «ready».
- Хендофф: аудит на зафиксированной ревизии в обычной сессии; либо роли запускаются отдельными процессами `opencode run --agent audit-… "<бриф>"` в каталоге проекта (если среда даёт shell — например, AetherShell); sessionID ролей сохранить (Фаза 3.5/re-audit).
- Если среда восстановилась до завершения — проведи отложенный аудит и обнови вердикт.
