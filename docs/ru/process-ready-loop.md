# Процесс: цикл прогонов до полного ready

Правило: аудит считается завершённым только когда **все роли** вынесли `verdict=ready`, а все находки обработаны. Никаких «остановок после N кругов»: цикл идёт до полного ready; при нерасхождении — эскалация, а не бесконечные повторы на том же состоянии.

Нумерация: «[N]» — шаги этого документа (`process-ready-loop.md`); «Фаза N» — фазы `call-mechanics.md`. Ссылки между документами указывают пространство имён явно.

## Дерево

```
[0] ФАКТ-ЧЕКЕР (актуальность премис/issue/PR)
     │
     ├─ задача устарела/сделана → СТОП (пересмотр задачи)
     ▼
[1] ЭМПИРИК ∥ ИНВАРИАНТЩИК (на состоянии X0)
     │        └─ конфликты? → АРБИТР (только спорные пункты); MAJOR → независимая верификация (перекрёстная, fail-closed)
     ▼
   ВЕРДИКТ: все ready и нет открытых MAJOR?
     ├─ ДА ──► для релизных ворот: [4] РЕД-ТИМ → [5] МЕТА
     │           (вход [5]: отчёты пары + отчёт ред-тима + свод reports/summary-<id>.md)
     │           ├─ SHIP ⟺ `meta.gate`=pass ∧ closing_list пуст/закрыт ∧ coverage_gaps приняты владельцем (запись в risks-<id>.md)
     │           ├─ иначе ship запрещён; адресный список несоответствий → правки/пересборка отчётов → повторная мета; повторный fail → эскалация владельцу
     │         для коммита/PR: SHIP, если правок после вердикта не было (ред-тим и мета не обязательны)
     └─ НЕТ ─► [2] ПРАВКИ (закрыть MAJOR; MINOR/NIT — закрыть или явно принять с обоснованием, запись в risks-<id>.md)
                ▼
           [2a] СВЕДЕНИЕ (если фиксеров было несколько: сведение веток по commit SHA → проверки на сведённом состоянии)
                ▼
           [3] НОВОЕ СОСТОЯНИЕ X1 (фиксы закоммичены/зафиксированы)
                ▼
           повтор [1] на X1 (оба аудитора, тот же бриф)
                ▼
           … повтор [1] на Xn, пока все роли не выдадут ready …

   [ВЕРДИКТ ЕСТЬ, СОСТОЯНИЕ ИЗМЕНИЛОСЬ] → повтор [1] (re-audit на новом состоянии) либо явное понижение вердикта
   [КОММИТ/PR] → строка «правок после вердикта нет»
```

На релизных воротах цикл тот же, плюс после первого полного ready — ред-тим; его находки (включая MAJOR — с независимой верификацией сессией противоположной роли) проходят такой же цикл правок/перепроверок, пока и он не выдаст ready.

## Критерий «полный ready»

1. Все роли (эмпирик, инвариантщик; на воротах — и ред-тим) — `verdict=ready`.
2. Открытых MAJOR нет. MINOR/NIT: закрыты либо **явно приняты** с причиной (запись в `risks-<id>.md`; в сводке/PR: «принято как долг: …»).
3. Все расхождения разрешены арбитром; недоказуемое → решение владельца: root оформляет вопрос, фиксирует риск и эскалирует.
4. Повторный прогон идёт **по состоянию после правок**, а не по старому диффу. Никаких «переголосований» на том же снапшоте. При нескольких фиксерах X1 достигается сведением их веток по commit SHA и проверками на сведённом состоянии; `closed` ставится после сведения.
5. На релизных воротах — `meta` = pass (`gate`=pass), `closing_list` пуст/закрыт, `coverage_gaps` приняты владельцем (запись в `risks-<id>.md`). **SHIP ⟺ `meta.gate`=pass ∧ `closing_list` пуст/закрыт ∧ `coverage_gaps` приняты владельцем (запись в `risks-<id>.md`); иначе ship запрещён.**
6. MAJOR-находки входят в правки только после независимой верификации; дефолт верификатора — «не подтверждена» (fail-closed).
7. Вердикт и верификация фиксируются вместе с ревизией состояния (хэш каталога/коммит); любая правка после фиксации вердикта → повторный прогон (re-audit) либо явное понижение вердикта.

## Когда цикл «не сходится» — эскалация (вместо стопа)

- Круг 3+ и всё ещё not_ready → арбитр разбирает **оставшиеся пункты по одному**: подтверждён / опровергнут (ложное срабатывание) / недоказуем.
  - «опровергнут» — находка снимается, фиксируется как ложное срабатывание аудитора (шум-дата для калибровки);
  - «недоказуем» — решение владельца: root оформляет вопрос, фиксирует риск и эскалирует;
  - «подтверждён» — обязательная правка, цикл продолжается.
- Признак бессмысленного продолжения: повторяются одни и те же ложные/недоказуемые находки без новых фактов. Это не «not ready», это дефект аудита — фиксируем и закрываем.

## Данные цикла (на каждый круг)

- Вход: дифф/состояние Xn + отчёт факт-чекера + список принятых рисков.
- Выход: два SGR-отчёта (эмпирик, инвариантщик) + разрешение арбитра (если был).
- Сводка оркестратора: `ready` / `not_ready(список открытых)`, что закрыто, что принято.
- На воротах дополнительно: свод `reports/summary-<id>.md` — вход меты `[5]` (Фаза 6); вердикты ворот — ред-тим (`closing_list`/`coverage_gaps`) и мета (`meta.gate`/`closing_list`/`coverage_gaps`).

## Замечания

- «Ready» — не «ноль находок», а «все находки обработаны»: закрыты, либо приняты осознанно.
- Разброс одиночных прогонов учтён самим циклом: следующий круг даёт новую выборку; поэтому цикл до сходимости, а не «один прогон в клетке».
- История подтверждает модель: PR #37 (bsl-context) — пара сказала ready с оговорками, приёмка нашла 8 дефектов, после правок и повторной приёмки — v0.22.0 и полный ready.
