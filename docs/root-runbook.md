# Root-runbook: инициирование аудита из главного агента

## Роли

- **Root (главный агент)** — не аудирует: формирует бриф, запускает субагентов, сводит отчёты; по «недоказуемым» — решение владельца: root оформляет вопрос, фиксирует риск и эскалирует. Ведёт реестр принятых рисков, вносит правки отдельными коммитами, решает «ship».
- **Субагенты** (read-only): `audit-factcheck`, `audit-empiric`, `audit-invariant`, `audit-arbiter`, (на воротах) `audit-redteam`, `audit-meta`.

## Шаблон брифа `case-<id>.md` (общий для всех шагов)

```
# Аудит: <задача/PR/релиз>
Состояние: <путь к песочнице/репо, коммит или диапазон; база для диффа>
Контекст: <что за изменение, цель, что заявлено автором>
Материалы: <дифф-файл, пути base/head; что недоступно (например, git-история)>
Ограничения: read-only; эксперименты во временном каталоге; сборка точечная; не публиковать
Формат отчёта: SGR (резюме + ```json по своей схеме)
```

В промпты пары добавляется блок «Факт-чек (пре-пасс): …» — 5–15 строк из отчёта факт-чекера.

## Чек-лист вызовов (порядок)

1. **Факт-чек**: `subagent(agent="audit-factcheck", prompt="<бриф> + сверь тезисы с живой реальностью: git/упстрим-issues/PR/код; что устарело, что уже сделано, какие обещания разошлись")`.
   - Если «устарело/уже сделано» → **СТОП** и пересмотр задачи (самая дешёвая экономия).
2. **Пара параллельно**: `subagent(agent="audit-empiric", background=true, prompt="<бриф> + блок факт-чека")` и то же для `audit-invariant`. Не опрашивать — ждать уведомления.
3. **Свод root'ом**: распарсить JSON-блоки; вычислить вердикты (ready/not_ready), открытые MAJOR, пересечения и расхождения (по location+механизму). Материализовать свод-артефакт `reports/summary-<id>.md` (определение — `call-mechanics.md` §4): по каждой MAJOR — {id, verifier_role, verdict, evidence}; refuted-список (явный, даже пустой); принятые риски; ревизия состояния (хэш каталога/коммит).
4. **Верификация MAJOR (перекрёстная, fail-closed)**: каждая MAJOR-находка подтверждается независимо **сессией противоположной роли** (не автором находки) — `subagent(agent="audit-<sibling>", sessionID=<сессия противоположной роли>, prompt="Находка <id> контрагента: <текст>. Evidence автора: <команда→вывод>. Ревизия состояния: <хэш каталога/коммит>. Подтверди или опровергни своим воспроизведением; дефолт — не подтверждена. Верни: {id, verifier_role, verdict: confirmed|refuted|partial|unavailable, evidence}.")`. `verifier_role` ≠ роль автора; `partial`/`unavailable` = «не подтверждена»; `refuted` — в список refuted для сводки; сбой/таймаут верификатора — «не подтверждена» + шум. Не подтверждена → в правки не идёт (спор → шаг 5, арбитр); статусы верификации пишутся в свод `reports/summary-<id>.md` (шаг 3). Если MAJOR-находка независимо воспроизведена обеими ролями в их собственных прогонах — взаимное подтверждение засчитывается как верификация (обе стороны в свод), отдельный прогон не требуется. sessionID при вызове обязателен: без него это новая сессия, а не продолжение — дефект шага.
5. **Арбитр — только при расхождениях**: `subagent(agent="audit-arbiter", prompt="Спорные пункты: <пункт → evidence A → evidence B>. По каждому: подтверждён/опровергнут/недоказуем + команда/цитата.")`. Вердикт свода (и верификация/арбитраж) фиксируются ДО правок и **вместе с ревизией состояния** (хэш каталога/коммит); любая правка после фиксации вердикта → повторный прогон (re-audit) либо явное понижение вердикта: до вердикта — не править.
6. **Правки** по порогу: микро — root сам; средние/крупные — `fix-runner` (вход: список «к закрытию» — id, локация, механизм, **класс/область** (пути + правило поиска однотипных мест), repro-до, критерий-после, severity — плюс границы и **бюджет/лимит (время, число правок)**; выход: fix-runner/v1 с before/after/`proof`/тестами). Отдельные коммиты `fix-<round>`; обновить реестр: `closed` / `accepted-risk` (с причиной). Root проверяет дельту до re-audit. Стенд раунда (если в комплекте поставляется проверочный стенд — инструменты `tools/kit-verify` и `tools/kit-sync` каталога комплекта; в раундах по другим проектам — только если стенд явно включён в границы вызова): baseline стенда в промпт фиксера (если вывод передан — фиксер не дублирует прогон); закрытие — синк копий и повторный прогон стенда; оба вывода — в поле `stand` отчёта. Статусы `fix-runner`: `needs_decision` → решение root (при споре — арбитр; если решение за владельцем — эскалация) с фиксацией в реестре рисков; `not_closed` → повторная итерация с тем же id; поле `out_of_scope` (замечено вне списка) → включить в следующий список «к закрытию» или эскалировать.
7. **Re-audit = resume те же сессии** (sessionID из шага 2): «Правки: <диапазон + фактический список изменённых файлов>. Проверь закрытие своих находок и отсутствие регрессий; верни обновлённый SGR.» — исторически так и делалось (продолжение сессий GLM/DS). sessionID обязателен: вызов без него (новая сессия вместо продолжения) — дефект шага.
8. **Повторяй шаги 3–7, пока не достигнут полный ready** (число кругов не ограничено; все роли ready, MAJOR=0). С 3-го круга нерешённые пункты — арбитр поштучно; повторяющиеся ложные — снять и записать как шум аудита.
9. **Ворота (релиз; порядок: ред-тим → мета)**: замороженный коммит → `audit-redteam` (мандат фальсификации + корпуса/стенды) → цикл по его находкам (MAJOR — с верификацией сессией противоположной роли) → `audit-meta` (на вход: отчёты + свод `reports/summary-<id>.md`; evidence, полнота, отсутствие «зелёные тесты = проверено»).
   - **SHIP ⟺ `meta.gate`=pass ∧ `closing_list` пуст/закрыт ∧ `coverage_gaps` приняты владельцем (запись в `risks-<id>.md`); иначе ship запрещён.**
   - `audit-meta` → fail: ship запрещён; адресный список несоответствий → правки/пересборка отчётов → повторная мета; повторный fail → эскалация владельцу. Ship — только после pass меты и выполнения ship-условия выше.

## Передача данных между узлами

- факт-чек → обоим аудиторам: короткий блок в промпт (5–15 строк);
- пара → root: SGR-JSON (машиночитаемо; сохранять в `reports/`);
- root → арбитру: **только спорные пункты** + evidence обеих сторон;
- root → re-audit: диапазон правок + краткое «что закрыто»;
- root → ред-тим: заявка автора + свод всех предыдущих кругов (объект фальсификации);
- root → мета: отчёты (пути) + свод `reports/summary-<id>.md`;
- root → fix-runner: список «к закрытию» (с классом/областью) + границы + бюджет/лимит (время, число правок).

## Тонкости

- Инструменты `audit_*` (если зарегистрированы плагином): ревизия состояния — `audit_snapshot` (aggregate), проверка SGR-отчёта — `audit_validate_report` (невалиден → resume сессии с перевыпуском SGR), sessionID/модель/стоимость ролей — `audit_sessions`; иначе — вручную, как прежде.
- Бриф и реестр рисков — файлами; отчёты субагенты возвращают в чат (правило `edit deny` в `permissions`; `shell` разрешён), root сохраняет нужное сам.
- «Слепые» прогоны — песочница без git-истории (без фикс-коммитов); re-audit — наоборот, дельта правок показывается.
- Вердикт root'а не подменяет вердикты аудиторов: пока обе роли не ready — цикл живёт (плюс правила эскалации из `process-ready-loop.md`).
- Тайминги ориентировочно: факт-чек ~1–2 мин, пара ~5–10 мин, арбитр ~1–3 мин на пункт, ред-тим — часы (только ворота).
- Универсальность: оба аудитора и добавляемые типы не содержат проектной конкретики; вся проектная специфика — в брифах и эталонах.
- **Преflight среды (Code Mode)**: если `subagent` недоступен — цикл не запускается; итог — «готово; штатный аудит отложен» (ревизия + компенсирующие проверки + план прогона), детали — `call-mechanics.md` §8.
- **Обязательный снимок конфигурации после установки/обновления агентов**: снимок конфигурации — `tools/config-guard` (если поставляется), иначе вручную сохранить копию конфигурации (иначе восстанавливать будет нечего). Источники не смешивать: определения агентов — каталог комплекта (`agents/`), конфигурация — `tools/config-guard` (если поставляется).
- **Покрытие снимка**: снимок конфигурации покрывает **конфигурацию** (глобальный каталог конфигурации вашего харнесса: определения агентов, основной конфиг, общие инструкции и пр.); доки комплекта (`docs/`, `agents/`, `README.md`) снимком НЕ покрыты — комплект остаётся источником, а отчёты прогонов сохраняются в `reports/`. Проверка снимка возвращает 0 при отсутствии расхождений и 2 при найденных проблемах.
- Хранитель конфигурации (если поставляется): восстановление по умолчанию докопирует только отсутствующие элементы и НЕ перезаписывает существующие; полная перезапись из снимка — только с явным подтверждением (`-Force` или аналог).
