# `eval/` — регрессионный стенд аудиторского контура

Стенд гоняет **живые роли плагина** (`audit-empiric`, `audit-invariant`, …) на
исторических учебных кейсах и измеряет, что контур реально находит и сколько это стоит.
Он отвечает на вопросы «не просела ли связка после правок промптов/схем/моделей» и
«какой у прогона cost/tokens/recall» — повторяемо и без ручной разметки.

Ничего из `lab/`, `agents/`, `lib/` стенд не меняет: он только читает кейсы, зовёт
роли и пишет в `eval/results/`. Стоимость/токены читаются **только на чтение** из
`~/.local/share/opencode/opencode.db` (`session_v2`).

## Структура

```
eval/
  run.ts                     стенд: песочницы, запуск ролей, разбор, отчёт
  derive.ts                  валидация SGR + матчинг для одного отчёта (общий код)
  matcher.ts                 нормализация отчёта + матчинг находок с ключом
  report.ts                  рендер report.md (общий код run/recompute)
  recompute.ts               offline-пере-матчинг сохранённого прогона (без LLM)
  selfcheck.ts               калибровка матчера на исторических отчётах
  README.md
  cases/<case-id>/           кейс: артефакты + бриф + ключ + манифест
    spec.md                  спецификация (эталон поведения)
    <impl>.ts                реализация под аудитом
    <impl>.test.ts           тесты «автора» из поставки
    README.md                заявка автора
    case.md                  бриф для аудитора (копируется в песочницу как промпт)
    reference-defects.md     ключ дефектов (в песочницу НЕ копируется)
    manifest.json            хэши файлов + машинные сигнатуры дефектов
  baselines/<name>.json      снятые эталонные прогоны
  results/<ts>/              результаты прогона: run.json, report.md, тексты отчётов
  dev-notes/                 протоколы самопроверки матчера + фикстуры
```

Кейсы:

| id | объект | MAJOR-дефекты ключа |
| --- | --- | --- |
| `csv-split-line` | `splitCsvLine` (CSV-строка) | `K1` (запятая в кавычках), `K2` (нет валидации форм) |
| `parse-duration` | `parseDuration` (001) | `S1` (нет покрытия входа), `S2` (`Infinity`), `S3` (O(n²) на вводе) |
| `normalize-tags` | `normalizeTags` (002) | `S1` (пустой элемент), `S2` (слепая тест-сетка) |

## Как запускать

```bash
# план без запуска (бесплатно)
bun eval/run.ts --dry

# один кейс, одна роль
bun eval/run.ts --cases csv-split-line --roles audit-empiric --tag probe

# полный базовый замер (3 кейса × 2 роли) со стоп-предохранителем и сохранением baseline
bun eval/run.ts --cases all --tag deepseek-baseline-2026-10-15 \
  --limit-usd 0.30 --baseline eval/baselines/deepseek-2026-10-15.json

# сравнение с уже снятым baseline (файл существует → режим сравнения)
bun eval/run.ts --cases all --baseline eval/baselines/deepseek-2026-10-15.json

# другая модель для роли (например, резервный провайдер)
bun eval/run.ts --cases all --model audit-invariant=deepseek/deepseek-flash

# то же через scripts в package.json
bun run eval -- --cases csv-split-line --dry
bun run eval:selfcheck

# пере-матчинг последнего прогона после правки сигнатур (без живых LLM-вызовов)
bun eval/recompute.ts
bun eval/recompute.ts eval/results/20261015-122730
```

Флаги: `--cases <ids|all>`, `--roles <r1,r2>`, `--model <role>=<provider/model>`
(можно повторять; `*` — модель для всех ролей), `--limit-usd <n>` (по умолчанию `0.30`),
`--tag <name>`, `--baseline <path>`, `--dry`.

Переменные окружения:

- `EVAL_OPENCODE_BIN` — путь к бинарю `opencode` (по умолчанию стенд сам ищет
  `opencode.exe`; `.cmd`-обёртка npm на Windows не подходит — она не принимает
  многострочный бриф).

Windows-детали запуска (обе воспроизведены на смоуках и важны для корректности):

- спавнится настоящий `opencode.exe`, а не `.cmd`-обёртка: `Bun.spawn` отказывается
  передавать в `.cmd` аргумент с символами `cmd.exe` (`` ` ``, `(`, `)`, `"`, переводы
  строк), а бриф многострочный;
- дочернему процессу принудительно выставляется `PWD` = путь песочницы. `Bun.spawn({
  cwd })` задаёт рабочий каталог процесса, но OpenCode определяет локацию сессии по
  `PWD`; без этого агент уходит в каталог фонового сервиса (репозиторий) и читает не
  ту песочницу.

Что делает прогон, по шагам:

1. Для каждой пары (кейс, роль) создаёт свежую песочницу
   `$TEMP/opencode/eval-runs/<ts>/<case>/<role>/` и копирует туда **все** файлы из
   `manifest.json.files` (`reference-defects.md` и `manifest.json` не копируются —
   ключ аудитору не виден).
2. Запускает `opencode run --agent <роль> -m <модель> --format json "<текст case.md>"`
   с `cwd` = песочница. Последовательно (не параллельно), таймаут 12 минут.
3. Собирает `sessionID`, сырой поток событий, финальный текст ответа, длительность и
   `cost`/`tokens_*` из `session_v2`.
4. Извлекает SGR-блок и валидирует его **штатным** `lib/report-schema.ts` против
   схемы роли (`<роль>/v1`): валидность отчёта — самостоятельная метрика.
5. Матчит текст отчёта с ключом (`matcher.ts`, общий код в `derive.ts`) и считает recall.
6. Пишет `results/<ts>/run.json` (всё машинно), `report.md` (таблица), тексты отчётов
   `<case>.<role>.md` и сырые потоки `<case>.<role>.raw.jsonl`.

Стоимость контролируется накопительно: при превышении `--limit-usd` прогон
останавливается, `totals.budgetExceeded = true`, оставшиеся пары не запускаются.
`run.json` перезаписывается после каждой ячейки, так что прогон переживает обрыв стенда.
Метрики по сохранённым отчётам можно пере-матчить без живых вызовов:
`bun eval/recompute.ts [results/<ts>]` (тем же `derive.ts`, включая baseline прогона).

## Базовый замер

`baselines/deepseek-2026-10-15.json` = `results/20261015-122730/` — 3 кейса × 2 роли,
модель `deepseek/deepseek-flash`, по одному прогону на ячейку, без ретраев.

| кейс | роль | SGR | cost | время | recall | recall MAJOR | непокрыто | кандидаты |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| csv-split-line | audit-empiric | валиден | $0.0313 | 220s | 1.00 | 1.00 | — | 1 |
| csv-split-line | audit-invariant | валиден | $0.0343 | 236s | 1.00 | 1.00 | — | 0 |
| normalize-tags | audit-empiric | валиден | $0.0213 | 475s | 1.00 | 1.00 | — | 0 |
| normalize-tags | audit-invariant | валиден | $0.0181 | 156s | 1.00 | 1.00 | — | 0 |
| parse-duration | audit-empiric | валиден | $0.0405 | 444s | 0.83 | 1.00 | S5 | 0 |
| parse-duration | audit-invariant | валиден | $0.0251 | 347s | 1.00 | 1.00 | — | 0 |

Итог: 6/6 валидных отчётов, `recall MAJOR = 1` во всех ячейках, суммарно **$0.1706**
(токены: in 102 669, out 177 199, reasoning 70 663, cache_read 2 155 648).

## Как добавить кейс

1. `eval/cases/<case-id>/` — положить `spec.md`, реализацию, тесты, `README.md`.
2. `case.md` — бриф для аудитора по образцу существующих: контекст, **ревизия (sha256
   файлов)**, бюджет и доступные инструменты, границы (песочница read-only,
   эксперименты в своём temp), контракт отчёта SGR. **Без подсказок о дефектах.**
3. `reference-defects.md` — ключ: по каждому дефекту `id`, severity, суть, ожидаемое
   поведение и сигнатуры. Этот файл в песочницу не копируется.
4. `manifest.json` — `files[]` (path/role/sha256; `case.md` тоже), `recovery`
   (как получена ревизия: `method` A/B/C или `original`, источник, `reconstructed`),
   `expected_major[]` и `defects[]` с машинными сигнатурами:

```json
{
  "id": "S1",
  "severity": "MAJOR",
  "class": "semantic",
  "title": "короткая формулировка",
  "signatures": [["1h30"], ["покрыти", "coverage", "остаток"], ["3600000", "3.?600.?000"]]
}
```

Семантика сигнатур: `signatures` — список групп; группа — альтернативы (regex,
случай не важен); **дефект найден, если совпала хотя бы одна альтернатива в каждой
группе**. Сигнатуры применяются к нормализованному тексту отчёта (нижний регистр,
типографские кавычки/тире → ASCII, пробельные серии схлопнуты). Подбирайте их по
**отличительным строкам evidence** (входы, возвращённые значения, имена механизмов),
а не по общим словам вроде «ошибка»/«тест» — иначе вырастет число ложных привязок.

Ключ должен быть проверяем: после правки сигнатур прогоните `bun eval/selfcheck.ts`
на исторических отчётах `dev-notes/fixtures/` — он покажет, что матчер ловит
ожидаемые MAJOR и не привязывает лишнего.

## Как читать метрики

`results/<ts>/report.md`:

| колонка | смысл |
| --- | --- |
| `отчёт валиден` | SGR-блок извлечён и прошёл схему роли (`да`/`нет (код)`); `E_PARSE` = блок есть, но это не валидный JSON; `E_INVALID` = структура не по схеме; `E_NO_JSON` = блока нет |
| `cost` | `session_v2.cost` сессии прогона (USD) |
| `время` | wall-clock прогона, `(timeout)` при срабатывании 12-минутного лимита |
| `recall` | доля дефектов ключа, чьи сигнатуры найдены в тексте отчёта |
| `recall MAJOR` | то же по MAJOR-дефектам ключа — главная метрика качества аудита |
| `непокрытые id` | дефекты ключа, не упомянутые отчётом (пропуски) |
| `кандидатов` | наблюдения отчёта, не привязанные ни к одному пункту ключа (`findings` + `invariants` со статусом `violated`) |

Примеры интерпретации:

- `валиден=нет (E_NO_JSON)`, `recall=0` — роль не выдала SGR (дефект формата/бюджета),
  а не «всё чисто».
- `валиден=да`, `recall MAJOR=0`, `кандидатов=5` — отчёт формально корректен, но
  нашёл не то, что заложено: смотрите кандидатов вручную (возможно, ключ неполон
  или формулировки роли разошлись с сигнатурами).
- `валиден=да`, `recall MAJOR=1`, `непокрыто: S3` — MAJOR найдены, пропущен менее
  важный пункт ключа (штатная картина: ресурсные MINOR находятся не всегда).

## Ограничения

- **`unmatched` — кандидаты, не ложные срабатывания.** Матчер не знает, верна ли
  находка; он лишь проверяет, упомянуто ли заложенное в ключ наблюдение. Разметка
  кандидатов — ручная.
- **Recall зависит от формулировок.** Сигнатуры калиброваны по историческим отчётам
  тех же ролей; при смене модели/промпта формулировки дрейфуют и recall падает даже
  при качественном аудите. `dev-notes/matcher-selfcheck.md` — точка калибровки.
- **Ключ неполон по определению.** Кейсы фиксируют известные дефекты ревизии, а не
  полный список возможных; часть MINOR/NIT в ключ сознательно не вынесена
  (контрактные пробелы, дублирующиеся evidence — см. `reference-defects.md` кейсов).
- **Тест-сетка из поставки — часть кейса.** У `parse-duration` ключ описывает дефект
  сетки на ревизии `759b3100…` (см. `recovery.note` в манифесте).
- **Стоимость.** Один прогон роли на `deepseek/deepseek-flash` — порядка $0.005–0.05;
  базовый замер из 6 прогонов укладывается в `--limit-usd 0.30`. Провайдеры бывают
  недоступны (например, исчерпан баланс) — стенд не ретраит: падение/таймаут
  фиксируется как есть.
- **Windows-специфика.** Бриф передаётся аргументом, поэтому на Windows нужен
  настоящий `opencode.exe` (см. `EVAL_OPENCODE_BIN`), а дочернему процессу обязательно
  выставляется `PWD` (см. выше) — иначе роль уходит в каталог сервиса.
- **Песочницы после прогона.** Файлы песочниц стенд не чистит автоматически (они —
  материал разбора); при необходимости удалите `$TEMP/opencode/eval-runs/<ts>/`. Живой
  фоновый сервис OpenCode держит каталоги сессий, поэтому пустые каталоги могут
  остаться залоченными до его рестарта.
